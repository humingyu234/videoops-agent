# AI 智能体协作与 Token 治理规范

> **适用范围：** 本规范适用于本项目中的人类协作、Codex、其他 AI 编程工具和 Superpowers 中文版工作流。<br>
> **核心目标：** 不削减代码质量、安全性、测试或验收门禁，只消除重复上下文、无效并发、重复审查和冗长输出造成的 Token（模型输入、输出和推理消耗的计量单位）浪费。<br>
> **权威性：** 本文是 AI 协作、并发、审查和 Token 治理的唯一权威来源；它不替代项目的安全、架构、接口、领域和编码规范。

## 1. 不可削减的质量门禁

- 不得因 Token 预算、进度压力或并发限制削减需求边界、公共契约、验收标准、测试、安全审查或交付前验证。
- 所有代码变更仍须满足项目既有的独立审查和验证要求；红色高风险任务另有专项审查要求。
- 开发过程可以运行相关的快速测试以缩短反馈时间，但交付前要求运行的完整构建、测试和关键路径验收不得减少。
- 无法运行的验证必须说明原因、影响范围和替代证据；不得将“未验证”描述为“已完成”。
- 质量门禁、漏洞修复、数据恢复和资金核对不受 Token 停损阈值限制。达到阈值时只停止扩展范围，不停止必要验证。

## 2. 术语与治理原则

- **工作任务：** 具有单一目标、明确边界和可验证验收结果的最小交付单元，不依赖计划编号、阶段名称或路线图名称。
- **任务卡：** 为一个工作任务提供的最小上下文包，包含目标、边界、权威来源、风险、验收、验证和协作安排。
- **可比任务：** 风险等级、任务类型、影响范围和验证深度相近的工作任务。
- **主力模型：** 当前团队认可用于业务判断、安全判断、实现和审查的高能力模型。
- **独立审查：** 审查者不能为同一任务的实施者，且结论必须基于验收、差异和实际验证证据。

所有任务先完成风险分级，再进入协作流程。风险不明确、跨多个账号或模块、影响外部系统或生产数据时，默认按红色高风险处理；只有项目负责人明确批准后才能降级。

## 3. 风险分级

### 3.1 红色高风险触发条件

下列清单是触发条件而非穷尽示例。任务命中任意一项即为红色高风险：

1. **身份、认证和授权：** 登录、注册、会话、令牌、密码、验证码、找回账号、角色、权限、数据范围、用户端与运营端隔离、管理员能力。
2. **安全控制和攻击面：** 密钥、签名、加密、敏感配置、防重放、防刷、防注入、跨站请求伪造、跨域、安全响应头、依赖漏洞、上传与文件安全。
3. **数据、隐私和内容访问：** 用户隐私、敏感数据、文件下载或预览、导入导出、跨账号数据、脱敏、保留、删除、恢复和内容安全。
4. **资金和资产：** 支付、退款、结算、账单、发票、优惠、价格、余额、积分、额度、冻结、扣减、退回、补偿、流水、对账和计费规则。
5. **不可逆或高影响操作：** 批量删除、覆盖、迁移、回填、恢复、生产数据修复、状态终结、批量执行或可能影响大量用户的操作。
6. **外部信任边界：** 第三方登录、支付渠道、AI 服务、对象存储、外部网络请求、回调、Webhook（回调接口）和外部身份凭据。
7. **共享契约和公共影响面：** 公共接口、数据库结构、共享状态机、缓存键、消息事件、公共配置、权限字典、跨模块规则和兼容性变化。
8. **高权限运营与审计：** 管理后台批量操作、跨用户操作、人工补偿、人工重试、审核、封禁、解封、审计日志和操作留痕。
9. **可用性、并发和恢复：** 限流、熔断、队列、任务调度、缓存、锁、幂等、重试、故障补偿或可能造成大面积不可用的改动。
10. **合规与外部义务：** 合规审批、数据出境、监管要求、合同义务、法务留存或影响用户法定权益的规则。

### 3.2 黄色和绿色任务

- **黄色中风险：** 已证明不命中任何红色条件，影响范围明确且可回退，但仍会改变用户可感知业务行为、接口消费或数据处理的任务。
- **绿色低耦合：** 已证明不命中任何红色条件，不修改公共契约、账号边界、资金资产、生产数据或不可逆状态，且可独立验证的隔离任务。
- 所有代码变更都必须经过项目既有的审查和验证；绿色不等于免审，只是可以在无共享状态时采用更高并发。

## 4. 各等级强制协作规则

| 等级 | 实施或混合阶段同一任务的并发智能体 | 模型要求 | 审查与验证 |
| --- | --- | --- | --- |
| 红色 | 最多 2 个：1 个实施、1 个独立审查或验证 | 业务、安全、资金和架构判断必须使用主力模型 | 一次规格/契约审查；一次安全、资金或对应专项审查；修复后只复核差异 |
| 黄色 | 最多 2 个 | 关键业务判断使用主力模型 | 独立代码审查、相关测试和交付前完整验证 |
| 绿色 | 最多 3 个，且任务间不得共享文件、契约、状态机或数据库变更 | 可使用经自动验证的机械辅助能力；最终判断仍由主力模型负责 | 项目既有审查、相关测试和交付前验证 |

- 并发上限指同时执行同一工作目标的智能体数量，不限制一个阶段内顺序参与的不同角色数量。
- 红色任务的审查智能体禁止派生新的智能体；任何嵌套派发都必须由任务负责人明确批准。
- 命中红色条件后，不得以“工作量小”“只是配置”“只是前端限制”降低等级。
- 黄色和绿色任务的纯审查阶段仍分别最多使用 2 个和 3 个智能体，不因没有实施写入而取消并发上限。

### 4.1 红色任务的标准纯审查模式

红色任务在不实施项目变更的纯审查阶段，最多可以同时使用 3 个智能体：1 个独立主审和最多 2 个独立专项审查者。主审不得是同一工作任务的原实施者，负责风险确认、任务卡把关、证据复核、发现去重、严重度校准和最终结论；专项范围必须在任务卡中预先声明且互不重叠。

该模式必须同时满足：

- 所有参与者只能读取源文件、执行构建／测试和诊断，不修改受版本控制内容或非测试外部状态。
- 测试写入只能通过项目安全夹具发生在专用环境，并须按夹具约定清理；构建产物和符合该条件的专用测试数据不视为实施变更。
- 任务卡必须说明为什么一个专项审查者不足；只需要一个专项视角时仍最多使用 2 个智能体。
- 专项审查者不得互相依赖或派生智能体；主审必须重新核对每项 `[必须修复]` 的代码、契约或测试证据并去重。
- 原实施者使用 `receiving-code-review` 验证反馈不构成独立审查，也不会自动适用该标准模式。
- Token 使用达到第 7 节的 70% 阈值后不得新增审查者；达到 85% 时必须形成负责人检查点；必要安全审查和验证不得停止。

符合上述条件属于治理内置标准模式，不需要逐次申请例外。超过 3 个智能体、允许实施写入或偏离其他条件时，必须按第 9 节取得负责人明确批准并记录。

### 4.2 红色任务的专项验证

- 身份、权限、数据归属任务必须验证无凭据、伪造凭据、过期凭据、错误角色、跨账号和直接接口访问等反向场景。
- 资金和资产任务必须验证幂等、重复请求、流水、失败补偿、重试、对账和重复扣减或重复退回。
- 数据、文件、迁移和批量操作必须说明回滚、恢复或补偿路径，并验证最小可行恢复场景。
- 外部服务和回调必须验证身份或签名、超时、重试、异常响应、伪造回调和失败后的状态一致性。
- 高权限运营操作必须验证权限、审计记录、数据范围、批量影响范围和误操作恢复。

## 5. 最小任务卡与上下文纪律

实施或审查开始前，任务负责人必须提供任务卡，至少包含：

1. 单一目标和明确的不做范围；
2. 风险等级、命中的红色触发条件或降级依据；
3. 权威规则、规格、契约和现有实现的直接引用；
4. 验收清单，包含成功和失败/越权等反向场景；
5. 允许影响的模块、公共契约和数据范围；
6. 依赖、实施者、审查者和并发上限；
7. 必须运行的测试、构建或人工验证；
8. 固定输出格式：完成项、风险、验证证据、阻塞项。

- 默认不得把完整历史对话、整份产品规划或无关大文档复制给智能体；任务卡引用权威来源，遇到不确定时再读取原文。
- 禁止无假设的全库扫描、重复探索和重复摘要。先说明要验证的问题，再读取最小相关范围。
- 输出不得重复输入材料或长篇复述推理；失败、阻塞或安全风险出现时，才附上最小必要证据。
- 任务卡信息不足时必须暂停澄清或读取权威来源，不能靠猜测补全。

### 5.1 跨会话进度与证据新鲜度

项目使用三类进度事实，职责不得互相复制：

- `docs/PLAN.md` 只维护阶段路线、依赖、验收信号和粗状态。
- `docs/EXECUTION.md` 是当前施工现场、阻塞、证据索引和下一动作的唯一实时来源，同时只允许一个活跃阶段。
- `docs/tasks/Tn-*.md` 冻结阶段目标、边界、反向场景和验证门禁，并在完成后保存验收记录。

状态固定为 `NOT_STARTED`、`IN_PROGRESS`、`VERIFYING`、`BLOCKED`、`DONE`、`NEEDS_REVALIDATION`、`DEFERRED`：

- `BLOCKED` 只表示当前范围内已没有可继续的安全动作；能继续诊断或修复时仍为 `IN_PROGRESS`。
- `DONE` 只在成功和必要反向场景都有与当前源码匹配的证据时使用。
- 已完成行为相关的源码、配置、环境或验收标准变化后必须转为 `NEEDS_REVALIDATION`；依赖其行为的后续阶段不得继续。
- `DEFERRED` 只能由项目负责人决定，智能体不能自行延期必做项。

每次施工开工必须确认绝对路径、分支、HEAD 和工作区，读取 `PLAN.md`、`EXECUTION.md` 与当前任务卡；发现未记录改动时先查来源，不得覆盖。每次收工必须检查 diff、运行任务卡规定的验证、记录失败和 `NOT_RUN`、更新下一条准确动作。纯解释或只读问答不改变施工状态。

每条证据至少记录：支持的验收项，`REAL/DEMO/MOCK` 环境，源码提交或 dirty diff 指纹，精确命令/测试/任务/产物，以及结果。AI 总结、静态阅读、“看起来正常”、只打开页面或 Mock 不能单独证明真实边界。日志和截图不得包含密钥、Token、私有 URL、用户隐私或未授权素材。

## 6. 审查、修复与交付

- 红色任务固定执行一次规格/契约审查和一次独立专项审查；专项审查类型随风险选择安全、资金、数据、迁移或可用性审查。
- 黄色和绿色任务仍按项目既有要求执行独立审查；不因 Token 控制取消审查。
- 最终审查结论只能标记为 `[必须修复]`、`[建议修改]` 或 `[仅供参考]`：
  - `[必须修复]` 用于安全漏洞、数据破坏或丢失风险、确定的逻辑／契约／兼容性错误，以及未通过的强制质量门禁；解决前不得合并或关闭任务。
  - `[建议修改]` 用于不阻塞合并的性能、可维护性、校验、可观测性或工程质量改进；不得伪装成 `[必须修复]` 扩大范围。
  - `[仅供参考]` 用于不要求本次采取行动的替代方案、命名／风格信息和背景说明。
- `[问题]` 只用于审查过程中的澄清；形成最终结论前必须转化为上述三类之一或撤销，不得进入最终问题清单。
- 没有代码、契约、验收或风险变化时，禁止发起新的完整复审。修复后仅复核修复差异及其相关测试。
- 交付结论必须列出实际运行的验证、结果和未验证项；测试失败或无法验证时不得关闭任务。

### 6.1 禁止无限流程与强制收口

以下规则是硬性终止条件。质量优先不等于允许无边界地继续分析、审查、返工、派发或等待；达到终止条件时，应把任务保持为未完成并交还负责人决策，而不是自行无限延长：

- **范围只冻结一次：** 开始实施或审查前必须明确本次目标、允许修改的文件、必须关闭的问题和不做范围。执行中发现的非阻塞改进记入 backlog（待办清单），不得自动升级为当前任务、扩大文件范围或新增交付物。
- **完整审查只进行一轮：** 一轮是按任务卡一次性完成预先声明的主审和专项视角；多个并行专项审查者仍属于同一轮。修复后只允许一次针对原发现及直接受影响测试的定向复核，禁止重新发起全量审查。
- **新问题不得借复核扩散：** 定向复核中新发现的问题，只有在它由本次修复直接引入，或有明确证据表明会造成安全漏洞、数据破坏、资金错误、契约不兼容时，才能成为新的 `[必须修复]`；其余一律进入 backlog，不阻塞当前收口。
- **同一问题最多自动返工两次：** 同一发现经历两次“修改 → 验证”仍未关闭时，必须停止自动修改，报告现状、证据和建议，由项目负责人决定继续、拆分或回退。禁止启动第三次自动返工循环。
- **同一失败最多重试两次：** 同一命令、工具调用、网络请求或环境检查在输入和环境没有实质变化时最多重试两次；再次失败必须停止并报告。禁止通过改写等价命令规避重试上限。
- **等待不得成为工作循环：** 单次等待或轮询最长 60 秒；外部状态连续两次无变化时，必须转做当前范围内的其他可交付工作，或停止并报告阻塞。用户明确要求持续监控且已约定轮询策略的任务除外。
- **小改动走轻量路径：** 对目标明确、可回退、且不改变运行时代码、业务契约、安全、数据或资金规则的文档／配置小改，只做一次简短的内联设计确认、一次直接修改和一次既定验证；不得新建规格、实现计划、子智能体或独立审查任务，除非用户明确要求。
- **用户要求收口时立即收口：** 用户表达“立即完成”“停止扩展”“直接提交”“很着急”或等价意图后，立即停止新增探索、新问题发现、新智能体和新审查；只关闭已经确认的 `[必须修复]`，运行一次预先约定的必要验证，然后交付。无法在现有范围内通过时，明确标记未完成并列出阻塞，不得自行继续扩展。
- **建议项不得拖延交付：** `[建议修改]` 和 `[仅供参考]` 默认进入 backlog；除非用户明确纳入本次范围，不得以它们为理由增加审查轮次、返工次数或等待时间。
- **每次扩展都需要新授权：** 超出任务卡的新增文档、计划、测试矩阵、审查视角、工具接入或公共契约修改，必须先说明新增成本和必要性并取得用户明确批准；“可能更完整”不构成授权。

## 7. Token 预算、记录与停损

- Token 预算按风险等级、任务类型、影响范围和验证深度管理，绝不按计划编号、阶段编号或单一全局上限管理。
- 同类可比任务完成至少 3 个后，根据真实记录形成**临时预算区间**；累计至少 10 个后，再形成**正式预算区间**。不同类别的区间不得互相套用。
- 平台可提供精确 Token 数据时，必须记录实际输入、输出和推理消耗；不可提供时，只能记录代理指标，并明确标注“非精确 Token 账单”。
- 代理指标至少包括：活动智能体数量、任务卡大小、引用资料范围、工具调用次数、审查轮次、返工次数、测试结果和从开始到验收关闭的时间。
- 使用到该任务预算区间的 70% 时，停止新增智能体、停止扩大范围并压缩非必要输出；使用到 85% 时，必须立即停止新增实施、审查和返工，交付“已完成／未完成／验证／阻塞”检查点。没有负责人明确追加预算，不得继续。
- 用户给出的时间、Token、轮次或完成时限是更严格的硬上限，优先于默认规则。平台不能提供精确 Token 时，使用活动智能体数、工具调用、审查轮次、返工次数和经过时间作为停损代理，不能以“无法精确计量”为由忽略停损。
- 未约定预算的文档或配置小改，默认不超过 1 名实施者、1 次修改、1 次验证和 30 分钟；预计无法满足时，必须在修改前或一旦确认超限时停止并请求负责人选择，禁止先无限执行再事后解释。
- 达到阈值不允许跳过必要测试、安全审查、资金核对、数据恢复或漏洞修复。未通过质量门禁的任务必须保持未完成状态。

## 8. 模型、工具与并发的使用边界

- 红色任务的业务、安全、资金、架构和审查判断必须由主力模型完成，不得使用降级模型替代。
- 能力较低或成本较低的辅助模型只可承担结果可自动验证的机械工作，例如受限范围内的索引、格式检查或重复项定位；它不能独立决定业务规则、安全结论、测试结论或发布结论。
- 所有外部检索、代码扫描和工具调用必须以任务卡中的待验证问题为范围；信息可能变化、需要精确出处或安全风险较高时，必须查权威来源。
- 只有在任务之间没有共享文件、契约、状态机、数据库变更、权限规则或顺序依赖时，才允许提升绿色任务并发。

## 9. 例外、紧急修复与真实强制力

- 符合第 4.1 节全部条件的标准纯审查模式不属于例外；超出人数、只读边界、独立性或任务卡条件时，才适用本节审批与记录要求。
- 任何并发、模型、审查或上下文规则的例外，必须由项目负责人明确批准，并记录原因、影响范围、剩余风险和额外验证。
- 不得以 Token 预算为理由豁免红色任务的质量门禁。
- 紧急修复不降低风险等级；先控制影响，再按红色流程补齐审查、测试和记录。
- 本 Markdown 文档提供制度约束，不声称已具备自动拦截能力。后续如建设自动校验，必须先明确其覆盖范围；在自动校验落地前，不得描述为“系统已强制阻止违规”。
