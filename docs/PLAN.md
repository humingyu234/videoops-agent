# VideoOps Agent 分阶段施工路线

本文只维护 T0～T7 的静态顺序、依赖和完成信号，不记录当前状态、运行证据、环境事实或下一步操作。当前施工现场只以 [EXECUTION.md](EXECUTION.md) 为准；当前辅助 runbook 也只由 `EXECUTION.md` 点名。

## 路线图

| 阶段 | 交付纵切面 | 核心非目标 | 完成信号 | 依赖 |
| --- | --- | --- | --- | --- |
| T0 | 无历史、脱敏、可追溯的新仓库基线 | 不改产品功能、不合并旧分支 | 来源、迁移提交和剩余安全风险记录在 `BASELINE.md`；公开发布仍由 T7 再扫描 | 无 |
| T1 | 固定样例跑通当前人工黄金链并锁定真实模型/工作流 | 不做 Agent UI、不顺手修产品缺陷或重构任务模型 | 真实 Provider 产生最终 MP4；两套任务 ID、耗时、哈希、ffprobe、工作流身份和反向场景有当前证据 | T0 |
| T2 | `DeliveryBrief`、`AcceptanceProfile` 与可恢复 `AgentRun` 最小契约 | 不做通用记忆、规则平台或多 Agent | 版本、归属、状态、幂等、重启恢复和迟到结果有迁移及边界测试 | T1 |
| T3 | 把脚本、声音、数字人、时间轴、渲染、查询和质量检查包装为类型化工具 | 不自 HTTP、不绕过 Service、不统一重写旧任务 | 每个工具有结构化契约、权限、幂等、稳定错误和真实任务/产物关联；未知工具和多余参数被拒绝 | T2 |
| T4 | 受约束的规划执行、最少澄清、异步暂停和恢复 | 不引入开放式执行器、任意命令或多 Agent | 能按输入跳过或阻塞步骤；取消/预算停止有效；重启后继续同一任务且 Provider 提交次数为 1 | T3 |
| T5 | 确定性媒体、内容版式、感知主观三层评价 | 不拍脑袋设置阈值、不使用黑盒总分 | 正反夹具能证明误报/漏报边界；真实合格样例通过；低置信主观项不自动判定 | T4 |
| T6 | 依赖感知的最多两次局部返工与三类人工批准 | 不无限重试、不整链盲目重跑 | 字幕失败只重做时间轴/渲染且上游 ID 不变；无改善、超预算或主观冲突转人工 | T5 |
| T7 | `/agent` 默认入口、可回放 Trace、比赛 Demo 与公开 GitHub 交付 | 不恢复全部产品页面、不夸大 Demo | 成功、局部修复、转人工、重启恢复四场景可复现；跨用户与批准边界通过；README、许可证、扫描、测试和视频与同一提交一致 | T6 |

## 固定顺序

```text
证明旧工厂真实可生产
  -> 冻结交付契约和可恢复运行状态
  -> 包装真实生产工具
  -> 让 Agent 受约束地编排
  -> 建立可解释验货标准
  -> 建立局部返工与人工批准
  -> 完成默认页面和公开交付证据
```

- 一次只施工一个阶段；进入后续阶段前，前置阶段必须有与当前相关源码、配置和环境匹配的证据。
- 未来阶段不预写详细施工卡。阶段成为当前阶段时，再依据当时源码、前置证据和风险生成或更新一份 runbook，并由 `EXECUTION.md` 唯一点名。
- 相关源码、配置、环境或验收标准变化后，旧证据必须重新验证，不能凭旧截图、Mock 或 AI 总结继续施工。
- T1 未完成前不实现复杂 Planner；T4 未完成前不做多 Agent；T5 未完成前不宣称自动验收；T7 发布门禁通过前不公开推送。
