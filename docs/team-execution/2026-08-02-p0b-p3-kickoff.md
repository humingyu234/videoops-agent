| F4 | A 完成 P3、`07`、三候选、优化、确认、版本树和文案库 | 停止本开工单；另开 P4 对账，不能直接执行旧 P4 计划 |

每次 rebase 只使用已签署 handoff 中的精确 head，不从聊天记录猜 SHA：

```powershell
git status --porcelain
# 输出必须为空
git fetch origin
git rebase <handoff 中的精确 head>
git merge-base --is-ancestor <handoff 中的精确 head> HEAD
if ($LASTEXITCODE -ne 0) { throw '当前分支没有包含要求的 handoff head' }
git push --force-with-lease origin <自己的分支>
```

`--force-with-lease` 只允许用于本人因 rebase 改写的功能分支，严禁用于 `main`。一旦某个提交 SHA 已写入 handoff 或独立 review，禁止再改写该提交；合并必须保留被审查提交的祖先关系。

真实集成／合并顺序固定为 `F0→F1→F2→F3→F4`，数据库顺序固定为 `01→02→03→04→04a→05→06→07`。开发切片可以重叠，不等于允许提前真实集成。

## 5. 共享文件 owner 协议

共享文件的完整清单只认主计划“共享文件单 owner 清单”，本开工单不复制，避免漂移。当前 F0／F1 的共享文件写 owner 为 A；B、C 对这些文件只读。后续每个门禁必须在 handoff 中重新记录 owner、基线、接收窗口和 reviewer，未记录就视为没有写权限。

需要共享文件时，开发不得先改后报，必须向 owner 发出下面五项：

```text
请求人：A／B／C
目标文件：仓库相对路径
原因：对应任务卡和缺失契约
最小改动：字段／类型／接口／组装点
所需门禁与时间窗：F1／F2／F3／F4
```

owner 用独立、精确提交完成共享改动；请求人 rebase 后消费。没有 owner 窗口时，不得复制一套本地公共类型、错误码、adapter、根页面状态或 Mapper 来绕开。

## 6. 实施、验证和提交纪律

- 严格按对应子计划的任务卡顺序执行 TDD；每张卡先取得可解释 RED，再做最小 GREEN，再运行该卡精确验收。不得用相邻测试或旧 XML 代替 fresh evidence。
- 所有 Java 集成测试使用子计划给出的准确模块、类名和 `-Pdev,local-integration-test`；只连接项目配置的本机受控 MySQL 8／Redis 7，禁止连接共享或生产环境，禁止自行引入 Docker 方案。
- writer 只能报告 candidate，不能把自己的复跑写成独立 PASS；reviewer 必须是未参与该实现的人。
- 每张卡固定输出四段：`完成项`、`风险`、`验证证据`、`阻塞项`。未阻塞时也明确写“无”。
- 精确暂存：`git add -- <本任务文件...>`；禁止 `git add .`。提交前核对 `git diff --cached --name-only` 只包含当前任务文件。
- 每人只 push 自己的功能分支并创建 Gitee 合并请求；禁止直接 push 业务提交到 `main`。
- 不提交个人 IDE 配置、构建产物或测试报告目录；仅提交计划明确要求的 Git metadata 证据。
- 同一问题最多自动修复／验证两轮；同一未变化失败最多重试两次；一次完整 review 加一次定向复核后必须收口。需要扩大范围时先取得用户批准，不能无限扫描、轮询、review 或顺手重构。
