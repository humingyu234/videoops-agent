# VideoOps Agent 决策记录

本文保存已经确认、会影响后续施工的产品与工程取舍，只解释“为什么这样做”。静态阶段顺序见 `docs/PLAN.md`，当前状态与证据只以 `docs/EXECUTION.md` 为准，当前阶段的目标、边界、验收和执行方法见该文件点名的辅助 runbook。

## D01：比赛只做一个明确行业纵切面

- 场景：品牌/电商运营人员把商品事实、品牌约束、人物形象和音色交给系统，得到一条可验收的竖屏数字人口播视频。
- 首期交付类型固定为 `image_to_digital_human_video`，默认目标为中文、9:16、MP4、带字幕；默认值必须展示并允许用户修改。
- 不把项目包装成通用视频 Agent，不训练新底模，不用多个互相聊天的 Agent 制造复杂度。

原因：评委需要看到行业任务闭环。窄场景更容易证明任务理解、真实工具调用、失败判断、局部返工和最终交付。

## D02：默认入口是 `/agent`，Studio 只作内部后备

- 参赛版不要求用户手动完成原七步流程。
- `/agent` 是唯一默认入口，承载目标、澄清、计划、执行、评价、批准和结果。
- 原 `/studio` 暂时从默认导航隐藏，但在依赖追踪和人工接管方案完成前不删除源码、不破坏接口。
- 运营端、RunningHub 发现市场、Electron 壳和独立形象空间不作为首期主演示依赖。

原因：比赛需要目标驱动的 Agent，同时现有 Studio 是排障、能力验证和人工接管的重要退路。直接删除会扩大风险，却不增加 Agent 价值。

## D03：复用视频工厂，只新增 Agent 控制面

- 复用认证、账号归属、形象、音色、脚本、数字人、时间轴、渲染、任务和资产能力。
- Agent 后端直接调用既有应用 Service，不通过“后端请求自己的 HTTP API”伪造工具调用。
- 既有任务和资产记录仍是执行事实；Agent 只记录 Brief、计划、动作、评价、批准和产物关联。
- 不先统一重构旧数字人任务与统一任务中心，Agent 观察层先兼容当前事实。

原因：约 70%～80% 的生产能力已经存在。比赛高价值增量是控制、恢复、验货、返工和证据，而不是重写供应商链。

## D04：用户提交交付目标，不提交七步参数

用户首屏提供：

- 自然语言目标；
- 已有形象或人物图；
- 音色或参考音频；
- 可选脚本、商品资料、品牌规范和参考素材；
- 时长、语言、比例、截止时间、预算、必须/禁止内容等硬约束。

Agent 将输入解析成版本化 `DeliveryBrief` 和 `AcceptanceProfile`。大模型可以提取候选值，但完整性由后端确定性规则判断。只问阻塞执行或显著影响结果的问题；一次最多三个问题、最多两轮。缺少商品事实时必须暂停，不能搜索或编造功效、价格、资质等事实。

原因：这样既保留自然交互，又避免模型自行宣布“信息完整”或把主观默认值藏起来。

## D05：一个可靠 Agent，受约束地计划和执行

- 首期采用确定性编排主干：状态机、白名单动作和后端业务不变量决定可执行范围；LLM 只在结构化边界内解析目标、选择候选动作和生成内容。
- LLM 不得执行任意 URL、SQL、文件路径或 FFmpeg 命令，不得直接改任务终态、资产归属或额度。
- 长任务必须持久化外部任务 ID 后暂停；网页关闭或服务重启后继续观察同一任务，不能重复提交付费 Provider。
- `Provider` 提交结果未知时先对账或转人工，禁止再次 POST。

原因：真正的 Agent 能力是可恢复地决定和行动，而不是一次长 HTTP 请求或前端定时器。

## D06：质量标准由三层证据组成

1. 确定性媒体门禁：文件可播放、容器/编码、分辨率、比例、时长、音轨、资产状态。
2. 内容与版式门禁：确认事实、必用/禁用内容、字幕完整与安全区、画中画位置和时间范围。
3. 感知与主观评价：身份相似、口型同步、音色一致、画面稳定和风格接近。

硬门禁失败不能交付。感知评价必须给出具体时间段、画面或文本证据和置信度；单个模型的黑盒分数不能独立触发返工。没有校准样本时，主观项只作建议或进入人工批准。

原因：Agent 无法天然等同于用户审美。可验证规则负责客观底线，用户确认负责主观标准。

## D07：只做依赖感知的有界返工

- 初始候选之外，最多产生两个质量返工候选；同一 `AgentRun` 最多评价三个候选。
- 字幕或画中画问题只重做时间轴与渲染；声音任务和数字人底片任务 ID 必须保持不变。
- 口型或画面稳定问题从数字人底片开始；声音问题从声音开始；事实错误必须先由用户重新确认脚本。
- 第一次修复无可测改善、无法定位故障、超时、超预算、约束冲突、只剩低置信主观判断、用户取消或外部提交状态未知时立即转人工。

原因：盲目全链重跑既慢又昂贵，也无法证明 Agent 理解依赖关系。

## D08：最少三个批准点

- 首次执行批准：冻结 Brief、脚本、素材、验收标准、预计时间/额度和返工上限。
- 条件批准：只用于改变已确认事实/脚本/形象/音色、昂贵上游返工、超时超预算或主观冲突。
- 最终交付批准：展示视频、三层评价、返工历史、成本/耗时和执行轨迹。

硬技术、安全、权限或资产归属门禁不能被“用户强行批准”为合格。

## D09：旧形象分支不直接合并

`origin/codex/avatar-space-provider-router@c15f55b` 的异步候选、私有资产、签名预览、人工确认和保存思路值得保留；旧任务引擎、SQL、配置、规则式“AI 对话”和 Java AWT Demo provider 不迁移。首期使用已有形象或上传图片；后续在当前主线重新实现候选批准工具。

原因：旧分支落后主线且有核心冲突，直接合并会把比赛主链变成迁移工程。

## D10：先证明人工黄金链，再写 Agent

- T1 必须用固定样例跑通真实 Provider 和真实最终 MP4，记录阶段任务 ID、耗时、失败点和产物摘要。
- 当前仓库不能证明 ComfyUI 的精确 checkpoint。测试夹具出现 `WanVideoSampler`，但不能据此宣称具体 Wan 版本；旧分支的 LTX 2.3 也不是当前主链证据。
- T1 必须导出实际 `数字人口播.json`，记录文件哈希、工作流 UUID、模型加载节点、checkpoint/LoRA 名称和环境标签。

原因：没有可重复的人工链路，Agent 只是自动化一条未知是否可用的流程。

## D11：比赛证据必须诚实可复现

至少演示：

- 资料完整后自动完成的成功场景；
- 故意注入字幕越界或禁用词后，只重做必要步骤的自动修复场景；
- 主观标准无法可靠判断时主动转人工的场景；
- 外部任务等待期间重启服务，恢复后仍观察同一 Provider 任务的工程证明。

真实 Provider、Demo provider、Mock、规则脚本和故障夹具必须明确标注。禁止硬编码成功轨迹、假日志或用 Mock 声称真实链路已通过。

## D12：公开仓库的发布门禁

- 不携带公司仓库原 Git 历史；旧凭据按已泄露处理并独立轮换。
- 所有密钥、私有 URL 和证书走环境变量或本地未追踪文件。
- 推送 GitHub 前重新执行 Secret 扫描、依赖/许可证核对，并补统一 LICENSE 与第三方声明。
- README 的能力声明必须与当前提交、可运行模式和证据一致。
