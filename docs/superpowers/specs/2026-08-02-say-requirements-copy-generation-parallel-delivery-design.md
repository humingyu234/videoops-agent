## 1. 目标与结论

本规格解决三名全栈开发在 P0-B、P0-C、P1、P2、P3 之间只能严格串行、导致人员等待的问题。

结论固定为：

- 开发开始时间可以重叠，验收、数据库升级、真实联调和合并门禁仍保持有序。
- P0-B 与 P0-C 负责公共安全和业务底座；P1、P2、P3 在公共契约冻结后分别建立独立开发泳道。
- P1、P2、P3 可以同时开发各自不依赖上游运行结果的切片。
- P2 接入真实知识路由与快照前必须通过 P1 门禁；P3 接入真实问卷上下文、收费任务和模型调用前必须通过 P2 门禁。
- 三名开发分别承担不同工作任务；红色高风险任务仍遵守“一个实施者加一个独立审查者”的单任务并发上限，不能把三个人同时放进同一个红色任务。

因此，团队采用“契约先行、错峰并行、分段集成”的方式。这里的并行是模块和切片并行，不是绕过依赖直接把未完成的上游能力接入生产链路。

## 2. 当前基线与必须先解决的问题

当前 main 已合入 P0-A，但现有 P0-B～P3 计划不能直接作为编码指令使用：

1. P0-A 的现行实现使用 identity.service 下的 IAppSessionService、IAppPermissionService 以及 identity.dto 下的 DTO；P0-B 仍引用旧的 identity.application 和 identity.model 类型。
2. P0-B～P3 计划仍包含 application、port、command、model 等平行业务层路径，与项目当前 RuoYi 分层硬规则冲突。
3. P3 计划直接依赖 P2 的 ScriptBranchEvidenceDecisionMapper，形成跨聚合数据访问；P3 必须改为只消费 P2 的稳定 Service 和 DTO。
4. 主计划把“允许开始开发”和“允许真实集成、合并”写成同一条串行链，未把可独立开发的纯逻辑、类型、Mock、局部页面和测试切出来。
5. P2 与 P3 都会接触用户端工作台，共享根页面、状态模型和公共服务文件；如果没有明确文件 owner，并行分支会产生高频冲突。

在上述计划与契约整改完成前，不启动 P0-B～P3 的业务代码实现。

## 3. 范围与非目标

### 3.1 本规格范围

- 定义三名开发在 P0-B、P0-C、P1、P2、P3 期间的持续工作安排。
- 把 P1、P2、P3 拆成“独立切片”和“集成切片”。
- 定义公共契约 owner、共享文件 owner、分支同步点、数据库迁移顺序和合并门禁。
- 定义前端 Mock、后端测试替身和跨阶段 DTO 的唯一来源。
- 为后续改写主计划及 P0-B～P3 子计划提供输入。
- 定义每个候选工作任务的风险、边界、审查和验证要求。

### 3.2 非目标

- 本规格不修改业务 API、字段、错误码、状态机或数据库结构。
- 本规格不实现 P0-B、P0-C、P1、P2、P3 的业务代码。
- 本规格不豁免 P0-A 的最终安全门禁证据。
- 本规格不允许在 P0-C 完成前调用真实模型或外部检索服务。
- 本规格不改变 P4 集成、灰度和上线范围。
- 本规格不把 Mock、测试替身或临时适配器作为生产兼容层长期保留。

## 4. 方案比较与采用决定

### 4.1 方案 A：全阶段严格串行

优点是分支冲突少，依赖简单。缺点是 P0-B 或 P0-C 由一人实施时，另外两人只能等待或频繁切换无关工作，无法满足三人团队的持续吞吐要求。

### 4.2 方案 B：P1、P2、P3 全量同时实现并直接合并

优点是表面上的启动速度最快。缺点是 P2 尚无可用的 P1 路由和快照，P3 尚无可用的 P2 分支与事实决定，数据库迁移和共享文件会互相覆盖；这会把编译替身、错误契约和临时字段带入主分支。

### 4.3 方案 C：契约先行、错峰并行、分段集成

先由契约 owner 冻结边界和共享文件，再允许每个阶段开发独立切片；到达上游门禁后，下游分支 rebase 并完成集成切片。该方案保持三人持续工作，同时保留权限、额度、任务、迁移和真实模型调用的强门禁。

本项目采用方案 C。

## 5. 并行交付总模型

### 5.1 两类顺序必须分开

开发顺序：

1. 独立切片只依赖已冻结的接口形状、测试 fixture 和本模块自有文件，可以提前开始。
2. 集成切片依赖上游真实实现，只能在对应门禁后开始。

交付顺序：

1. P0-B 工作区与组织授权。
2. P0-C 任务、额度、方向和草稿底座。
3. P1 已发布知识路由与不可变快照。
4. P2 问卷分支、补充字段和接受事实上下文。
5. P3 三候选、版本、确认和文案库。
6. P4 集成与上线。

开发可重叠不代表交付顺序改变。

### 5.2 契约 owner

每个冻结点临时指定一名契约 owner，职责固定为：

- 维护公共文档、共享错误码、共享 TypeScript 类型和跨模块 DTO 的唯一变更。
- 把现有计划中的旧分层路径映射到 RuoYi 标准路径。
- 组织前端、后端和联调三个视角的审查。
- 发布可追溯的冻结提交和变更摘要。
- 拒绝未经过审查的跨模块字段、状态、任务或迁移变化。

其他开发不得在同一时间修改冻结中的公共契约文件。

### 5.3 实际编码隔离

本次规格文档改动直接在当前工作区完成。进入三人业务编码后，每名开发必须使用独立的 codex/ 前缀分支；使用 worktree 或独立克隆由开发环境决定，但不同开发不得在同一工作目录同时写文件。

每个下游分支在冻结点后 rebase 上游冻结提交。禁止通过复制文件或手工挑选部分 DTO 来规避 rebase。

## 6. RuoYi 分层与跨模块契约冻结

### 6.1 统一分层

P0-B～P3 的业务聚合只能使用：

- domain：贫血 Entity 和简单内聚判断。
- dto：稳定的跨模块 Service 数据契约，统一使用 DTO 后缀。
- mapper：本聚合的数据访问。
- service：使用 I...Service 命名的服务接口。
- service.impl：使用 ...ServiceImpl 命名的实现。
- 端侧 HTTP 模块可另用 domain.bo、domain.vo 和 controller。

禁止新增 application、application.impl、port、adapter、command、model 作为平行业务层。外部 AI 或检索供应商的直接 client、provider、请求和响应只能位于 ai-video-infra 的直接集成边界。

### 6.2 跨阶段稳定服务

计划改写时至少冻结以下服务边界：

| 阶段 | 稳定 Service | 稳定 DTO 责任 |
| --- | --- | --- |
| P0-B | IWorkspaceAuthorizationService | 当前工作区、工作区上下文、资源动作、成员和授权修订 |
| P0-C | IAiTaskService、IAiTaskExecutionDispatcher、IAiTaskAttemptService、IQuotaBillingService、IDirectionCatalogService | 任务创建结果、执行租约、任务修订快照、结果引用、额度和方向快照 |
| P1 | IKnowledgeRoutingService、IKnowledgeSnapshotService | 路由请求、A／B／C 路由结果、快照创建和快照读取 |
| P2 | IQuestionnaireContextService、IEvidenceReviewService | 当前分支、问答与补充修订、接受事实和 factId 到 decisionRevision 的准确映射 |
| P3 | IScriptGenerationService、IScriptVersionService、IUserScriptQueryService | 文案任务、不可变版本、确认和用户文案查询 |

具体字段沿用原规格已有业务语义，并在公共契约冻结任务中逐项映射；实现计划不得继续引用旧类型名或自造同义包装对象。

### 6.3 跨聚合访问规则

- P3 不得注入或调用 P2 的 Mapper。
- P2 不得直接访问 P1 的知识表或 Mapper。
- P1 不得绕过 P0-C 自行创建任务或计费记录。
- P0-C 不得反向依赖 P1、P2、P3 的业务表。
- 前端页面不得直接拼接接口路径、解包统一响应或判断后端状态字符串。

## 7. 三人持续工作时间线

人员以“开发 A／B／C”表示，不形成长期模块归属；每个阶段结束后可以重新分配。

### 7.1 阶段 R：计划与契约整改

| 开发 | 当前工作 | 输出 |
| --- | --- | --- |
| A | 改写 P0-B／P0-C 的 P0-A 消费映射和 RuoYi 路径 | 可执行的 P0-B／P0-C 计划与冻结清单 |
| B | 只读核对后端依赖、迁移、反向场景和 P1 服务边界 | 独立契约审查结论 |
| C | 只读核对前端文件归属、Mock、状态矩阵和 P2／P3 冲突 | 独立前端／联调审查结论 |

其中 A 与 B 属于同一个红色 R0 任务，分别担任实施者和独立审查者。C 执行单独的只读 R1 审计任务，不修改 R0 文件、不参与 R0 实施；其审计结论只作为契约 owner 后续吸收的证据。因此阶段 R 不是三个参与者同时实施同一个红色任务。

阶段 R 结束条件：

- P0-A 实际 IApp...Service 与 DTO 已逐项映射。
- P0-B～P3 的旧业务层路径已从可执行步骤中移除。
- 公共契约和共享文件已有唯一 owner。
- P0-A 最终安全门禁证据可追溯。

### 7.2 阶段 B：P0-B 实施期间

| 开发 | 主任务 | 可做 | 不可做 |
| --- | --- | --- | --- |
| A | P0-B 工作区授权 | P0-B 全量实现和测试 | 创建草稿、任务、额度或下游业务资源 |
| B | P1 独立切片 | 知识版本纯逻辑、发布校验、确定性路由／快照单测、平台 API 类型、Mock 和局部页面 | 接入 P0-C 免费导入任务、执行完整迁移链或真实任务恢复 |
| C | P2 独立切片 | 问答类型、答案规范化、完整性策略、模型 Schema 校验、前端 Mock 和局部组件 | 真实知识路由、数据库基线、收费任务、真实模型或检索调用 |

P0-C 可在 P0-B 的服务和 DTO 冻结后编写契约测试、状态机测试和迁移设计，但持久化集成、资源创建和合并必须等待 P0-B 完成门禁。

### 7.3 阶段 C：P0-C 实施期间

| 开发 | 主任务 | 输出 |
| --- | --- | --- |
| A | P0-C 任务、额度、方向和草稿底座 | 02 之后可执行的 03／04 迁移及任务／额度门禁 |
| B | P1 独立切片继续 | 知识核心、平台页和测试；P0-C 集成点保持未接线 |
| C | P2 独立切片继续 | 问卷纯逻辑、API 类型、Mock、需求步骤和测试 |

此阶段仍不启动真实模型、搜索或 P3 冻结输入链路。

### 7.4 阶段 K／Q／S：P0-C 契约冻结后的三泳道

| 泳道 | 负责人 | 并行内容 | 集成门禁 |
| --- | --- | --- | --- |
| P1 知识 | B | 知识聚合、05 迁移、发布、路由、快照、导入、平台接口与页面 | P0-C 最终门禁 |
| P2 问卷 | C | 独立切片继续；P1 通过后接入真实知识、任务、06 迁移和证据链路 | P1 最终门禁 |
| P3 文案 | A | 结果校验、版本树纯逻辑、scripts API 类型、Mock、候选／编辑／优化／文案库局部组件 | P2 最终门禁后接入冻结输入、07 迁移、收费任务和模型 |

此阶段三人分别拥有不同模块和文件，可以同时开发。审查在冻结点轮换进行，审查者不得审查自己的实现。

## 8. 各阶段独立切片与集成切片

### 8.1 P1

独立切片：

- 知识条目、不可变版本、审核发布和退役规则。
- 确定性路由和快照的纯逻辑及单元测试。
- 平台端 knowledge API 类型、Mock、管理页和完整页面状态。
- 05 迁移文件的设计与审查。

集成切片：

- 依赖 P0-C 的免费 knowledge_import 根任务、冻结输入和入队。
- 依赖 P0-C 方向目录的发布绑定校验。
- 在 01～04 之后执行 05 迁移和真实集成测试。

### 8.2 P2

独立切片：

- 答案规范化、稳定哈希、完整性策略和分支规则的纯逻辑测试。
- question-generation-1 Schema、严格输出校验和固定测试样本。
- studio API 类型、query key、mock/aivideo-studio.ts。
- 方向、单题、补充字段、证据审核、费用确认和任务进度局部组件。

集成切片：

- 依赖 P1 的已发布目录、IKnowledgeRoutingService 和 IKnowledgeSnapshotService。
- 依赖 P0-C 的收费任务、操作槽、额度和 provider attempt。
- 在 05 之后执行 06 迁移、真实问卷和安全事实检索测试。
- 向 P3 输出稳定 IQuestionnaireContextService、IEvidenceReviewService 和 DTO，不输出 Mapper。

### 8.3 P3

独立切片：

- A／B／C 三候选结构、长度、事实引用、相似度和内容校验器。
- 不可变版本树、人工编辑、确认规则和删除引用规则的纯逻辑测试。
- scripts API 类型、adapter、query key 和独立 mock/aivideo-scripts.ts。
- 候选页签、版本编辑、优化操作和用户文案库局部组件。

mock/aivideo-scripts.ts 至少覆盖：

- 生成中和修复中。
- A／B／C 三候选及每套三个标题。
- 额度不足和价格版本变化。
- 上下文过期、403 和版本冲突。
- 空文案库、搜索无结果和分页。
- 删除确认和存在下游引用时拒绝删除。

集成切片：

- 依赖 P1 的路由和知识快照。
- 依赖 P2 的当前分支、修订、接受事实和决定修订映射。
- 依赖 P0-C 的收费任务、冻结输入、执行租约、尝试上限和额度结算。
- 在 06 之后执行 07 迁移。
- 接入真实生成、单次修复、优化、确认和下游准确版本引用。

## 10. 冻结点、rebase 与合并门禁

### F0：P0-A 映射与 P0-B／P0-C 契约冻结

- P0-A 最终安全证据可追溯。
- P0-B 消费的 IApp...Service 和 DTO 与 main 实现一致。
- P0-B／P0-C 使用 RuoYi 标准分层。
- 工作区、资源动作、任务、额度、错误和 TypeScript 公共适配规则冻结。

### F1：P0-B／P0-C 最终门禁

- P0-B 通过个人／组织切换、成员修订、对象授权、跨账号和 SQL 数据范围测试。
- P0-C 通过草稿幂等、任务恢复、操作槽、额度锁定／结算／释放和不可变流水测试。
- P1／P2／P3 分支共同 rebase F1。
- F1 前禁止真实模型和搜索调用。

### F2：P1 门禁

- 05 迁移通过。
- 只有已发布文案知识可路由。
- A／B／C 路由确定且知识快照可追溯。
- P2 rebase F2，移除 P1 测试替身并接真实 Service／DTO。
- P3 只可开始接 P1 DTO，不得接 P2 未完成能力。

### F3：P2 门禁

- 06 迁移通过。
- 每答一题才生成下一题、相同答案复用、不同答案分支正确。
- 补充字段、证据决定、当前分支修订和 factId 到 decisionRevision 映射通过。
- P3 rebase F3，移除 P2 测试替身并开始真实冻结输入、任务和模型链路。

### F4：P3 门禁

- 07 迁移通过。
- 一次生成原子保存 A／B／C 三套文案，每套三个标题。
- 冻结上下文、事实引用、版本树、确认、优化、权限和下游引用测试通过。
- P4 才能开始最终集成。

合并顺序固定为 F0 → F1 → F2 → F3 → F4。下游功能分支可以提前存在，但不得在缺失对应门禁时合入主分支的真实集成代码。

## 11. 数据库迁移规则

全新测试环境和升级验证固定执行：

01 → 02 → 03 → 04 → 05 → 06 → 07

其中：

- 02 属于 P0-B。
- 03／04 属于 P0-C。
- 05 属于 P1。
- 06 属于 P2。
- 07 属于 P3。

每个泳道只能编辑自己的迁移文件。可以提前编写和审查下游迁移，但不能在缺少上游迁移的数据库基线上声明集成通过，也不能把同一张表分散到两个阶段迁移中。

所有后端集成测试只连接本机 MySQL 8 的 ai_video_test 和 Redis 7 隔离逻辑库，不使用 Docker、Testcontainers、WSL 或其他容器、虚拟化环境。

## 12. Mock、fixture 与替身规则

- Mock 形状必须从冻结的 HTTP BO／VO 或 TypeScript 类型派生，不维护第二套字段命名。
- 跨模块后端测试使用稳定 Service 接口和 DTO 的受控 fake；不得在生产源码中提交临时空实现。
- 下游分支不得复制上游 Entity、Mapper 或数据库表来让编译通过。
- Mock 必须覆盖成功、失败、权限不足、额度不足、修订冲突和恢复场景。
- 到达 F2 或 F3 后，相关替身必须从真实集成测试中移除，并增加契约零漂移扫描。
- 未完成的替身不得以兼容层名义进入主分支。

## 13. 前端完整状态矩阵

所有页面共同覆盖：

- 鉴权恢复、加载、初始空、搜索无结果、网络或 5xx 失败与重试。
- 401 单次退出、403 权限不足。
- 提交中防重复、取消不作为失败、成功后按统一 query key 刷新。

P1 另覆盖：

- 分页、导入解析中、导入冲突和导入失败。
- 草稿、审核、发布、退役、引用检查和二次确认。

P2 另覆盖：

- 工作区切换、方向空、排队、运行、成功、失败、取消、任务过期。
- 额度不足、费率重确认、相同答案复用、改答分支警告和修订冲突。
- 补充字段、证据空、证据失败和证据冲突。

P3 另覆盖：

- 上下文未就绪、生成中、修复中、无候选。
- 额度不足、费率变化、上下文过期、保存中和确认中。
- 版本树、文案库空、搜索无结果、分页、删除确认和下游引用阻止。

## 14. 风险与最小任务卡
