# 声音播放与文案精确同步修复规格

## 1. 目标与范围

修复声音管理页的两个确定问题：

- 连续点击文案、点击进度条或拖拽进度条时重复创建音频实例，导致多人声叠加。
- 文案时间轴按字符平均分配，无法与真实语音节奏、停顿和标点准确对应。

本次覆盖 Whisper Worker、Java 后端持久化与用户端声音页面。继续复用现有异步转写调度，不接入 IndexTTS2，不增加质量检测、额度、任务中心或克隆流程。

## 2. 根因

### 2.1 多重人声

`useVoicePlayback.play()` 每次跳转都会创建新的 `Audio`，但创建前没有同步暂停和释放旧实例。`audioRef` 随后被覆盖，旧实例失去控制并继续播放。进度条拖动会在 `pointerdown`、多个 `pointermove` 和 `pointerup` 中反复调用该路径，因此操作越多叠加越明显。

### 2.2 文案不同步

当前 `getVoiceWords()` 使用“总时长 ÷ 字符数”生成时间点。参考 HTML 也是模拟时间轴，不包含真实音频。真实录音存在不同语速、停顿和断句，平均分配无法实现精确同步。

## 3. 方案

### 3.1 单实例播放器

- 页面级播放器任何时刻最多拥有一个活动 `HTMLAudioElement`。
- 切换声音时，必须先暂停旧实例、清除事件处理、移除音频源并释放引用，再加载新声音。
- 同一声音点击文案或拖动进度条时复用当前实例，只更新 `currentTime`，不得重新请求访问地址或创建 `Audio`。
- 首次访问地址尚在加载时，后续拖动只更新“最后期望位置”；加载完成后仅创建一次实例并跳到最后位置。
- 使用代次标识忽略过期异步响应；播放失败刷新地址时也必须先释放失败实例。
- 播放进度以真实 `audio.currentTime` 为准，通过单一动画帧循环更新 UI。

### 3.2 Whisper 真实时间戳

Worker 调用 `faster-whisper` 时启用 `word_timestamps=True`，将结果规范化为：

```json
{
  "text": "微信",
  "startMillis": 120,
  "endMillis": 480
}
```

规则：

- 丢弃空白词元，保留有效标点和中文内容。
- `startMillis >= 0`，`endMillis >= startMillis`，并裁剪到音频总时长。
- 显示文案和时间戳词元来自同一次 Whisper 结果，避免两套文本来源。
- Worker 继续返回完整文本、语言和总时长，并新增 `words` 数组。

### 3.3 Java 持久化和接口

- `av_voice` 新增可空 JSON 字段 `transcript_timeline_json`。
- `VoiceTranscriptionResultDTO`、领域 `VoiceDTO` 和用户端 `VoiceVo` 增加时间戳列表。
- 转写成功时，在同一次状态完成更新中写入文本、语言、时长和时间戳。
- Java 调用 Worker 时传入 `wordTimestamps=true`，并校验词元边界和总时长。
- 声音详情及列表响应增加 `transcriptTimeline`：`[{ text, startMillis, endMillis }]`。
- 新增 `POST /api/voices/{voiceId}/transcription/resync`，请求携带 `expectedRevision`。仅允许当前用户所属工作区、具备 `aivideo:voice:transcribe` 权限且状态为 `ready` 的声音进入 `pending`，继续由现有调度器异步处理。
- 失败声音仍使用现有 `/transcription/retry`；不新增第二套失败状态。

### 3.4 前端同步规则

- 有 `transcriptTimeline` 时，页面直接渲染真实词元；点击词元跳到 `startMillis`。
- 高亮以 `startMillis <= audio.currentTime < endMillis` 判定，已读状态以 `endMillis <= audio.currentTime` 判定。
- 拖动进度条只 seek 当前音频，不创建播放器。
- 旧记录没有时间戳时显示普通文案和“重新同步”操作，不展示伪精确逐字高亮。
- 人工编辑文案成功后，后端清空时间戳；页面提示“文案已修改，重新同步后恢复逐字高亮”。
- “重新同步”必须确认“将按录音重新识别并覆盖当前文案”，防止覆盖人工修改而无提示。

## 4. 状态、异常和兼容

- 新上传声音：`pending -> transcribing -> ready`，成功后同时拥有文本和时间戳。
- 旧声音：保持 `ready`，不自动批量覆盖；用户主动重新同步后补齐时间戳。
- 人工修改：保持 `ready`，清空时间戳，不伪造同步数据。
- 转写失败：沿用 `failed`、失败原因和现有重试入口。
- Worker 返回非法时间戳：本次转写按不可重试响应异常处理，不写入部分结果。
- API 新增字段为可选字段，旧前端不会被破坏。

## 5. 测试与验收

### 前端

- 连续点击同一文案词元只创建一个 `Audio`。
- 连续拖动进度条只修改一个实例的 `currentTime`。
- 切换声音前旧实例已暂停并释放。
- 过期访问地址响应不能启动播放。
- 真实时间戳决定点击位置、当前词和已读词。
- 无时间戳时不显示伪逐字同步，并能触发带确认的重新同步。

### Worker 与后端

- Worker 返回规范化的词元时间戳。
- Java multipart 请求启用时间戳并正确解析、校验。
- 转写完成原子写入时间戳；人工编辑清空时间戳。
- 重新同步校验权限、归属、状态和修订号。
- 数据库迁移和 schema contract 测试通过。

### 真实联调

- 对现有测试录音执行一次重新同步。
- 连续点击文案、点击进度条和持续拖拽时，始终只有一个人声。
- 服务器 Whisper 日志出现一次有效转写请求，接口返回时间戳，页面点击文案能跳到对应语音。

## 6. 任务边界与治理

- 风险等级：黄色。触发依据是数据库字段、Worker 响应、Java DTO 和前端契约联动变更，但不涉及资金、额度或跨租户能力。
- 契约 owner：声音模块。
- 允许修改：Whisper Worker、声音领域/接口/迁移、用户端声音播放器与相关测试、本文规格及实现计划。
- 不修改：IndexTTS2、克隆、质量检测、额度、任务中心和其他工作台模块。
- 验证门禁：Worker 测试、相关 Maven 测试与打包、前端播放器/时间轴/声音库测试、真实录音联调、`git diff --check`。
- 反向验收：没有时间戳或人工编辑后的文案不得继续表现为“精确同步”；连续操作不得遗留不可控音频实例。

## 7. 规格自检

- 无 TODO、待定项或占位符。
- 数据来源、状态流转、人工编辑和旧数据兼容规则一致。
- 范围仅覆盖本次声音播放与文案同步问题。
- “精确同步”明确指 Whisper 时间戳驱动，不再指字符平均估算。
