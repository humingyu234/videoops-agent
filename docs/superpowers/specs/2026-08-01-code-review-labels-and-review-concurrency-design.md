# Code Review 标签与风险感知并发治理设计

## 1. 背景与目标

当前 `docs/AI_AGENT_GOVERNANCE.md` 将最终审查结论标记为“阻塞”“建议”“信息”，而项目 `chinese-code-review` skill 使用 `[必须修复]`、`[建议修改]`、`[仅供参考]`。两套术语语义接近但形式不一致，容易造成审查输出不符合治理主文档。

本次变更需要同时解决两个问题：

1. 将项目最终 Code Review 结论统一为 `[必须修复]`、`[建议修改]`、`[仅供参考]`。
2. 保留风险分级和质量门禁，同时为不实施项目变更的专项审查阶段提供受控并发能力，兼顾高风险任务的审查覆盖与执行效率。

## 2. 范围与非目标

### 2.1 本次范围

- 修改 AI 协作治理主文档中的最终审查标签及定义。
- 明确 `[问题]` 只用于审查过程中的澄清，不属于最终审查结论。
- 明确实施或实施与审查混合阶段继续遵守现有风险并发上限。
- 为红色高风险任务不实施项目变更的纯审查阶段增加最多 3 个智能体的标准受控模式。
- 检查 `AGENTS.md`、`RULES.md`、`docs/AI_CODING_RULES.md`、`docs/DOCUMENT_MAP.md` 和 Superpowers 模板是否存在需要同步的重复规则。

### 2.2 非目标

- 不降低或跳过任何任务的风险分级。
- 不减少安全审查、反向场景、测试、构建或验收门禁。
- 不允许实施智能体借“审查”名义增加并发写入。
- 不修改业务代码、业务契约或当前 P0-A 验收范围。
- 不把治理正文复制到入口文档或技能文件中。
- 不修改 `.codex/skills/**` 下的 Superpowers 中文版或其他上游 skill；项目差异只能通过项目治理文档约束。

## 3. 风险等级

本次属于红色高风险治理变更。它会影响身份、权限、缓存、兼容性等红色任务的审查组织方式，并改变所有后续审查的公共分类契约。

风险控制如下：

- 治理主文档仍是唯一权威来源。
- 风险等级和专项验证要求保持不变。
- 纯审查并发模式必须不修改受版本控制内容或非测试外部状态，且范围不重叠、过程可审计。
- 修改后运行项目开发规范校验，并对规则引用和术语做静态检查。

## 4. 最终审查标签

最终 Code Review 结论只能使用以下三类标签：

- **`[必须修复]`**：安全漏洞、数据丢失或破坏风险、确定的逻辑或契约错误、兼容性故障，或者未通过的强制质量门禁。该问题解决前不得合并或关闭任务。
- **`[建议修改]`**：不阻塞合并的性能、可维护性、校验、可观测性或工程质量改进。不得为了扩大范围而伪装成 `[必须修复]`。
- **`[仅供参考]`**：替代方案、命名或风格信息，以及不要求本次采取行动的背景说明。

`[问题]` 仅用于审查过程中澄清作者意图。主审必须在形成最终结论前将其解决、转化为上述三类之一，或明确撤销；它不能出现在最终问题清单中。

## 5. 风险与 Review 技能边界

`chinese-code-review` 负责中文表达、优先级标注和审查总结，不改变任务风险等级、验证深度或合并门禁。该 skill 作为上游能力保持只读；项目治理主文档负责规定其在本项目中的最终输出边界：`[问题]` 仅用于过程澄清，最终必须转化或撤销。

`receiving-code-review` 负责在实施反馈前验证其技术正确性，不能将外部反馈直接视为必须执行的命令，也不能以节省 Token 为由跳过代码核对或相关测试。反馈涉及新的公共契约、安全边界或影响范围时，必须重新评估任务风险。

两个 Review 技能均不得忽略风险。风险决定审查范围和验证深度；并发规则只决定如何组织已经确定的审查工作。

## 6. 并发设计

### 6.1 实施或混合阶段

现有并发上限保持不变：

- 红色任务最多 2 个智能体，通常为 1 个实施者和 1 个独立审查或验证者。
- 黄色任务最多 2 个智能体。
- 绿色低耦合任务最多 3 个智能体，且必须不存在共享文件、契约、状态机或数据库变更。

只要任一智能体正在实施代码、文档、契约、数据库结构或非测试外部状态变更，就不属于纯审查阶段，不能使用下述模式。构建产物和经过项目安全夹具校验、可清理的专用测试数据不视为实施变更。

### 6.2 红色任务的标准纯审查模式

红色任务在不实施项目变更的纯审查阶段，可以最多同时使用 3 个智能体：

1. 1 个独立主审，负责风险确认、任务卡、证据复核、发现去重、严重度校准和最终结论；主审不得是同一工作任务的原实施者。
2. 最多 2 个独立专项审查者，分别覆盖任务卡中预先声明且不重叠的审查视角，例如核心业务行为与启动装配/迁移兼容。

启用该模式必须同时满足：

- 任务卡说明为什么一个专项审查者不足，并列出两个互不重叠的审查范围。
- 所有参与者只能读取源文件、执行构建/测试和进行诊断，不修改受版本控制内容或非测试外部状态；测试写入只能发生在符合项目安全规则的专用环境，并须按夹具约定清理。
- 两个专项审查者不得互相依赖，不得派生新的智能体。
- 主审不得直接拼接子审查结论；必须对每项 `[必须修复]` 重新核对代码、契约或测试证据。
- 如果任务只需要一个专项视角，仍使用最多 2 个智能体，不得为了并发而拆分。
- Token 使用达到治理第 7 节的 70% 阈值后不得再新增专项审查者；达到 85% 时必须形成检查点并由负责人决定是否追加预算；必要安全审查和验证仍须完成。
- `receiving-code-review` 由原实施者处理反馈时不构成独立审查，也不会仅因处于验证步骤而自动适用该标准并发模式。

该模式是治理规则内置的标准审查方式，不需要逐次申请例外。它只放宽纯审查阶段的并发数量，不是风险降级，也不减少独立性、专项审查或交付验证要求。超过 3 个智能体、允许实施写入或偏离其他启用条件时，仍须按治理主文档的例外流程取得负责人明确批准并记录原因、影响范围、剩余风险和额外验证。

并行专项审查优化的是互不依赖视角的等待时间，不保证降低 Token 总消耗。只有预计减少串行等待且两个专项范围都确有必要时才能启用；否则保持默认并发上限。

## 7. 审查与验收场景

规则变更后至少验证：

1. 治理主文档的最终审查标签只使用 `[必须修复]`、`[建议修改]`、`[仅供参考]`。
2. `[问题]` 被明确限制为过程性澄清标签。
3. 红色任务的风险分级、主力模型、安全审查和专项验证要求没有被删除或弱化。
4. 有实施写入时仍最多 2 个智能体，不能套用标准纯审查模式。
5. 纯审查阶段最多为 1 个主审加 2 个不重叠的专项审查者。
6. 审查者不能派生智能体；主审必须复核并去重发现。
7. Token 使用达到 70% 后不得新增审查者，达到 85% 后必须形成负责人检查点。
8. 超过标准模式边界时仍进入治理例外审批和记录流程。
9. `RULES.md` 与入口文档仍只薄引用治理主文档，不复制详细规则。
10. `scripts/validate-development-standards.ps1`、术语扫描和 `git diff --check` 全部通过。
