## 8. 认证数据流与安全行为

### 8.1 密码登录

1. 用户输入账号与密码。
2. 页面只做必填和空白校验；账号仍允许用户名、手机号或邮箱，不照搬参考页仅手机/邮箱的格式限制。
3. 提交时调用现有 `authApi.login({ identifier, password })`。
4. 固定以 `persistent=false` 调用现有 `authSession.save`：保存前清除同 key 的旧 `localStorage`/`sessionStorage` 值，新 Token 只进入 `sessionStorage`，不得写入 `localStorage`。
5. 保存 Token 后立即调用现有 `authApi.me()` 验证会话。
6. 验证成功后使用现有同步状态提交逻辑更新 `@@initialState`。
7. 使用现有同源安全回跳校验；非法、协议相对或空用户路由回退到 `/studio`。

### 8.2 必须保持不变的安全逻辑与失败矩阵

- 同一时刻只允许一个登录请求，重复提交直接忽略。
- `/api/auth/login` 尚未成功时不得清理调用前已存在的会话；尤其匿名登录返回 `46129` 时只能显示中性凭据错误，不得误删预存 Token。
- Token 已保存后，`/api/auth/me` 返回空用户或发生非 403 失败时清理刚保存的 Token。
- Token 已保存后，`/api/auth/me` 返回 403 时保留受控 Token 并进入现有受保护结果页，不泄露上游详情。
- 401、`46128`、`46129` 使用统一中性凭据错误，不区分账号不存在、密码错误或账号不可用。
- `46130` 显示受控的客户端不可用提示。
- 网络错误与业务错误分开，不依据中文 `msg` 分支。
- 已存在的会话被匿名登录失败影响时，继续遵循现有 `authSession` 保护规则。
- 用户端固定使用既有 App Client ID、`Authorization: Bearer <token>` 和 `/api/auth/login`、`/api/auth/me`；运营端与用户端的 Client ID、Token key 和会话存储不得混用。

### 8.3 微信扫码建设中

## 9. 页面状态与反馈

- 初始态：默认选中“账号密码”，账号和密码为空；登录按钮按参考页保持蓝色启用外观。空表单点击后先触发表单校验，不调用 API；只有真实提交中才禁用按钮。

- 提交中：主按钮显示加载并禁用，输入与页签按需要锁定，防止重复提交和状态切换竞态。
- 登录成功：保留现有状态同步与跳转，不提前展示虚假成功。

- 密码已修改、会话已退出通知：继续只接受固定白名单查询值，不渲染任意 query 文本。
- 权限不足：沿用现有登录后 403 处理；登录页自身不伪造授权结论。
- 加载、空数据、搜索无结果和分页：登录页没有服务端列表，不适用；不得为满足模板而制造空列表或分页 UI。
