# VideoOps Agent 参赛交付纵切面设计

> **历史设计来源：** 本文记录 2026-08-14 当时确认的讨论与设计，不是当前进度、当前源码能力或施工状态声明。当前产品范围见 `docs/PROJECT.md`，取舍见 `docs/DECISIONS.md`，技术边界见 `docs/ARCHITECTURE.md`，静态路线见 `docs/PLAN.md`，实时现场只见 `docs/EXECUTION.md`。

**日期：** 2026-08-14

**历史状态（2026-08-14）：** 当时已确认，可进入分阶段施工；后续执行仍须按实时 HEAD 重新核对

**风险：** 红色。触发外部 AI Provider、文件与资产归属、异步状态、幂等、重试、预算、公共 API 和最终交付。

## 1. 目标

把现有图生数字人口播生产能力改造成一个面向品牌/电商运营的交付 Agent。用户给目标、事实、素材和限制，系统负责澄清、计划、调用真实工具、观察长任务、验收、有限返工并请示，最后交付 MP4、质量报告和执行轨迹。

本设计只覆盖一个首期类型：`image_to_digital_human_video`。不建设通用工作流市场、多 Agent 群聊、新底模训练或自动发布平台。

## 2. 用户体验

默认入口从 `/studio` 改为 `/agent`。首屏不是七步向导，而是一张交付单：

```text
自然语言目标 + 人物/音色/资料/参考素材 + 硬约束
  -> 少量阻塞问题
  -> 合并确认卡（Brief、脚本、素材、验收、时间/额度、返工上限）
  -> Agent 运行轨迹
  -> 评价与必要的局部返工
  -> 用户最终批准和下载
```

原 Studio 保留为内部高级编辑、排障和人工接管入口，不进入参赛默认导航。首期不依赖运营端、RunningHub、Electron 或独立形象空间。

## 3. 输入与澄清

`DeliveryBrief` 保存原始目标、内容事实、素材归属、输出要求、限制、可见默认值和阻塞问题。确认后按版本冻结；任何确认内容变化都创建新版本，旧任务的迟到结果只能成为历史候选。

关键字段：

- `rawGoal` 与固定的 `deliveryType`；
- `subject`、`audience`、`coreMessages`、`callToAction`；
- `mustKeepFacts`、`prohibitedContent`、语气和语言；
- 有归属校验的 `portraitId`、`voiceId` 或 `audioAssetId`；
- 已确认脚本版本；
- 时长、9:16、字幕、可选画中画、MP4；
- 截止时间、额度上限、0～2 次自动返工；
- `assumptions`、`blockingQuestions`、服务端规范化 `briefHash`。

大模型只生成候选结构，后端规则判断完整性。一次最多三个阻塞问题、最多两轮；仍不完整就进入 `WAITING_INPUT`。缺形象、音色用途不明、事实不足、约束冲突、预算/期限明显不可行、权限/归属/格式/安全失败时必须阻塞。中文、9:16、字幕开启等可采用默认值，但必须在确认卡展示。

## 4. Agent 控制面

```text
Agent UI
  -> AgentRun / PlanStep / ToolInvocation / Evaluation / Approval / RunEvent
    -> 类型化工具适配器
      -> 既有应用 Service
        -> 既有任务、资产、Worker 与外部 Provider
```

建议状态：

```text
PLANNING
-> WAITING_INPUT
-> WAITING_INITIAL_APPROVAL
-> EXECUTING
-> WAITING_EXTERNAL_TASK
-> EVALUATING
-> REPAIRING
-> WAITING_CONDITIONAL_APPROVAL
-> WAITING_FINAL_APPROVAL
-> COMPLETED | FAILED | CANCELLED
```

Agent 不直接操作数据库、不绕过业务 Service、不修改既有任务终态。每次工具调用必须有结构化输入/输出、归属、幂等键、超时、费用/额度预估、可重试错误、外部任务 ID 和产物 ID。长任务提交后先保存身份再暂停；恢复时观察同一任务。

## 5. 最小工具集合

- 规范化并校验 Brief；
- 选择/校验形象；
- 选择音色或创建参考音频任务；
- 生成或确认脚本；
- 创建数字人底片任务；
- 创建时间轴与字幕/画中画配置；
- 创建最终渲染任务；
- 查询任务与读取授权产物；
- 运行质量检查；
- 发起受限重试、局部返工和批准请求。

LLM 只能选择白名单动作和结构化参数，不得执行任意 URL、SQL、路径或命令。首期采用确定性状态机作为执行主干，避免先引入复杂 Agent 框架。

## 6. 验收契约

`AcceptanceProfile` 是已确认 Brief 的版本化快照，包括：

- 技术与内容策略版本；
- `hardCriteria`：期望值、检查方法和证据要求；
- `subjectiveCriteria`：用户期望、重要度、参考素材和决策模式；
- 所有硬门禁必须通过；
- 单个模型分数不能独立拒绝、通过或触发返工；
- 截止时间、额度和返工次数上限。

首期稳定检查代码：

```text
media.playable                 media.container_codec
media.video_dimensions         media.audio_present
media.duration                 content.script_integrity
content.must_include           content.prohibited
subtitle.text_integrity        subtitle.safe_area
subtitle.timing                perceptual.identity_similarity
perceptual.lip_sync            perceptual.voice_consistency
perceptual.visual_stability    style.tone_match
```

前两组硬门禁使用 `ffprobe`、文件摘要和确定性规则。感知项必须返回时间段/画面/文本证据、置信度和评价器版本；在 T1 真实样本与 T5 固定夹具校准前，不设置拍脑袋的自动阈值。

## 7. 局部返工与停止

| 失败 | 可复用 | 最小失效范围 | 自动策略 |
| --- | --- | --- | --- |
| 容器/编码/混流 | 脚本、声音、底片、时间轴 | 最终渲染/转码 | 可自动 |
| 字幕漏字、时序、安全区 | 脚本、声音、底片 | 字幕/时间轴→渲染 | 可自动 |
| 画中画位置或时长 | 脚本、声音、底片 | 时间轴→渲染 | 可自动 |
| 口型、闪烁、稳定性 | 脚本、已确认声音 | 底片→时间轴→渲染 | 预算内最多一次 |
| 发音、噪声、音色 | 形象、脚本 | 声音及全部下游 | 条件批准 |
| 事实、禁用词、核心信息 | 形象 | 重新确认脚本及全部下游 | 不自动改事实 |
| 形象/音色选错或越权 | 无 | 返回用户选择 | 禁止自动 |
| 低置信主观冲突 | 当前候选 | 先细化标准 | 禁止盲试 |
| Provider 提交状态未知 | 原任务与幂等身份 | 对账/人工 | 禁止重新 POST |

一个运行最多有一个初始候选和两个质量返工候选。租约恢复、继续轮询和幂等回放不计质量返工，但不能创建新收费根任务。无改善、无法定位、超时、超额度、硬约束冲突、低置信主观判断、取消或提交状态未知时立即暂停并请示。

## 8. 批准与人工接管

- 首次执行批准：冻结 Brief、脚本、素材、AcceptanceProfile、预计时间/额度和返工上限。
- 条件批准：只在昂贵上游重做、确认内容变化、超时超预算或主观冲突时出现。
- 最终交付批准：展示候选视频、三层评价、返工历史、成本/耗时和完整轨迹。

硬技术、安全、权限和归属失败不能通过人工按钮直接改成合格。用户可以修改 Brief、终止或进入 Studio 人工接管。

## 9. 故障与恢复

- 外部任务失败按稳定错误类型区分可重试、不可重试、需对账和需人工。
- 每个收费提交使用稳定幂等键；提交结果未知不重发。
- AgentRun、当前步骤、工具调用和外部任务 ID 必须持久化；服务重启后恢复同一运行。
- 旧 Brief 版本的迟到回调不能覆盖当前产物。
- 用户取消后停止新动作；能否取消外部 Provider 必须按真实能力记录，不能伪造“已停止”。
- 日志和轨迹只保存脱敏摘要，不记录 Token、密钥、私有 URL 或原始敏感素材。

## 10. 比赛验收场景

### A. 正常成功

用户提供目标、人物图、参考音频和商品事实。Agent 只询问真正缺失内容，一次确认后调用真实工具，完成评价并交付真实 MP4。轨迹显示任务 ID、产物 ID、阶段耗时和输入输出摘要。

### B. 自动局部修复

在真实底片的 Demo 夹具中故意造成字幕越安全区。评价器拒绝第一版并定位 `subtitle.safe_area`；Agent 只重做字幕/时间轴/渲染。第二版通过，声音和数字人底片任务 ID 保持不变。故障夹具必须显式标注。

### C. 主观标准转人工

技术与内容门禁通过，但“稳重品牌语气”只有低置信偏差且没有确定修复动作。Agent 停止昂贵重跑，展示对比证据，让用户接受、细化标准后新建版本，或进入 Studio。

### D. 工程恢复

Agent 等待真实外部任务时重启 Java 服务。恢复后仍是同一 AgentRun、同一 Provider 任务，Provider 提交次数保持 1。

## 11. 评测与效果指标

首期建立至少 10 个固定商品 Brief、4 个故障案例（资料缺失、禁用词、Provider 超时/未知、字幕越界）和 1 个服务重启案例，并与当前七步人工模式执行相同任务对照。记录：

- 闭环任务成功率、首次交付通过率和自动修复成功率；
- 用户手工操作次数与必须批准次数；
- 局部重做比例，以及未变化上游任务/资产的复用率；
- 总交付时间、各 Provider P50/P90 和额度/成本；
- 规则/评价器的误报与漏报；
- 外部失败与服务重启后的恢复率；
- 重复收费或重复根任务次数，目标为 0。

不在 PPT 里预写“效率提升 80%”等无样本结论。所有比赛数字必须能回到固定数据集、当前提交和运行证据。

## 12. 非目标与演进顺序

先证明人工黄金链，然后依次实现数据契约/状态、类型化工具、编排/恢复、评价、返工/批准和 Agent UI/比赛证据。首期不合并旧形象空间分支，不做多 Agent、长期向量记忆、自动发布、通用规则平台或模型训练。
